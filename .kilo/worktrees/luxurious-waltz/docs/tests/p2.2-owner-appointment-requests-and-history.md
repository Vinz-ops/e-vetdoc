# [P2.2] Deliver owner appointment requests and appointment history

## Why This Task Mattered

Owners must be able to request appointments for their own pets and see their history without ever seeing another owner's data. Without this task, the appointment flow had no owner-facing UI and no server-side ownership enforcement, creating both a usability gap and a privacy risk.

## What Was Verified

- **RLS on `services` table**: public read policy applied so owners can fetch available services; confirmed by seeding data becoming visible in the dropdown.
- **`requestAppointment` service guard**: validates that the submitted `pet_id` belongs to the authenticated owner before inserting; prevents forged pet IDs.
- **Appointment list tab**: `listOwnerAppointments(userId)` is called for owners so only their own appointments are returned by Supabase (enforced by RLS + service filter).
- **Appointment detail page**: server-side check compares `appt.owner_id` to `profile.id`; mismatched IDs return 404.
- **Time picker**: replaced third-party `react-time-picker` with native `<input type="time">` after user reported UX issues.
- **All 6 manual test cases**: passed by owner user (see Human Evidence).

## Human Evidence

- [x] Navigated to "Request appointment" as an owner → form loaded with only linked pets in the dropdown and available services selectable.
- [x] Submitted a valid appointment request (pet, service, preferred date/time, reason) → appointment created with status `requested`; no error.
- [x] Navigated to `?tab=appointments` → own appointment appeared in the list with correct pet name, service, status badge, preferred date/time.
- [x] Clicked "View details" on the appointment card → detail page rendered with patient info, schedule, service, notes, and timeline sections; no other owner's data visible.
- [x] Tested owner-to-pet ownership validation → only linked pets selectable; no mechanism to submit a foreign `pet_id` through the UI.
- [x] Verified cross-owner isolation at detail URL level → accessing a non-owned appointment ID returns 404 (server-side guard in `page.tsx`).

## Result

Pass. All six owner-facing verification steps completed successfully; ownership validation, RLS, and the appointment history/detail views work correctly for the MVP scope of [P2.2].
