# P1.1 identity reconciliation

## Role model

E-VetDoc has exactly three application roles: `admin`, `veterinarian`, and `owner`. The role is stored in `public.profiles`, not in editable Supabase Auth metadata. New profiles default to `owner` through the database default and the existing `handle_new_user` trigger.

For the MVP, a profile has one canonical role. Dual-role staff are deliberately not represented by a client-editable flag or a permissive fallback. An administrator does not receive veterinarian-only clinical authority; a later staff-role-assignment design must be explicitly approved before dual-role access is supported.

## Compatibility migration

`0001_reconcile_identity_schema.sql` safely converts the template enum:

| Existing value | E-VetDoc value |
| --- | --- |
| `admin` | `admin` |
| `user` | `owner` |
| `NULL` or an unexpected legacy value | `owner` |

The migration drops the old enum default before temporarily converting the column to text, normalizes all existing values, and then creates the E-VetDoc enum. This makes the conversion safe for a populated template database.

The follow-up policy migrations protect the canonical role from owner self-service updates. Their security-definer helpers live in the private database schema, rather than as public RPCs.

## Template-domain reconciliation

The vehicle/SaaS template tables for leads, bookings, gallery items, blog posts, analytics events, and audit logs are removed. `notifications` remains because it is a general delivery primitive. The existing `services` table remains temporarily as the only service catalogue; P2.1 will decide whether to evolve or replace it. No replacement appointments or competing service catalogue is introduced by P1.1.

The connected development schema also contains `pets` and `pet_owners` from the interrupted prior session. They are tracked locally to avoid live-schema drift, but their owner-management behavior and acceptance tests remain P1.5 work; P1.1 does not claim that feature complete.
